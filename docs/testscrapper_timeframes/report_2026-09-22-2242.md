**Comando ejecutado:**

```bash
python3 wztest_scraper_filters_v3.py
```

**Fecha:** 2026-09-22 · UTC 22:31–22:40 · ET 18:31–18:40 (NYSE cerrada, datos del cierre diario vivos)
**Endpoint utilizado:** `POST https://scanner.tradingview.com/america/scan?label-product=heatmap-stock`
**Símbolos de prueba:** `NASDAQ:NVDA`, `AMEX:SPY`, `NASDAQ:QQQ`

### Nota de archivo: el POST batch `/scan` NO era el problema — era la URL

La corrida v2 (reporte 2343) refutó `POST /scan` con HTTP 404 (Q16). Pero ese era el endpoint **genérico**. El que usa el heatmap de TradingView de verdad es `POST /america/scan?label-product=heatmap-stock`, y **este sí acepta `symbols.tickers`, `columns` con sufijos `|TF` y `filter` con tiempo**. La duda Q16 se reabre y se cierra a favor: **el batch POST es viable**, solo que hay que llamar a la ruta correcta.

## 1 · Hallazgo principal: los filtros SÍ aceptan temporalidades (`campo|TF`)

### Test J · Evidencia directa

| Filtro | Coincidencias / 3 | Interpretación |
| --- | --- | --- |
| `RSI > 60` (sin TF) | 1 | filtra sobre el valor global del símbolo |
| `RSI\|15 > 60` | 1 | filtra sobre la barra de 15 min |
| `RSI\|60 > 60` | 3 | filtra sobre la barra de 60 min (todos arriba) |
| `close > 700` | 2 | precio global |
| `close\|15 > 700` | 2 | precio de la barra de 15 min |
| `volume\|15 > 1e6` | 3 | volumen de la barra de 15 min |
| `change\|15 > 0` | 0 | cambio de la barra de 15 min |
| `ADX\|15 > 25` | 3 | ADX de la barra de 15 min |
| `MACD.macd\|15 > 0` | 0 | MACD de la barra de 15 min |

Respuesta del mismo request con columnas `RSI|15`, `RSI|60`, `volume|15` (filtro `RSI|15 > 0`):

```
NASDAQ:NVDA  close=228.87  RSI|15=53.47  RSI|60=74.57  vol|15=4,805,009
AMEX:SPY     close=773.38  RSI|15=50.17  RSI|60=67.43  vol|15=2,695,849
NASDAQ:QQQ   close=747.46  RSI|15=75.24  RSI|60=83.30  vol|15=2,329,908
```

Los valores devueltos son distintos entre `|15` y `|60`, y coherentes con un RSI intradía. El filtro con TIME en el `left` filtra sobre la barra de ese timeframe, no sobre un valor global.

### Confirmación adicional (Test M)

Filtro sobre el **universo completo americano** (sin `symbols.tickers`):

```json
{
  "columns": ["name","close","RSI|15","volume|15","market_cap_basic","change"],
  "markets": ["america"],
  "filter": [{"left": "RSI|15", "operation": "greater", "right": 70}],
  "sort": {"sortBy": "market_cap_basic", "sortOrder": "desc"},
  "range": [0, 10]
}
```

→ `totalCount: 1078`, primeras filas con `RSI|15 > 70` de verdad (TSM 81.3, MU 74.1, AMD 70.7, …).
**El filtro con tiempo escala sobre los ~19.738 símbolos del mercado** con una sola llamada.

## 2 · Catálogo de temporalidades que acepta el filtro (Test K)

Patrón idéntico en **RSI, ADX, volume y MACD.macd**: las temporalidades válidas son las mismas.

| Timeframe | ¿Discrimina en el filtro? |
| --- | --- |
| `\|1` | ✅ |
| `\|2`, `\|3`, `\|10`, `\|45`, `\|180`, `\|360`, `\|720` | ❌ no devuelven datos con operador `greater` |
| `\|5` | ✅ |
| `\|15` | ✅ |
| `\|30` | ✅ |
| `\|60` | ✅ |
| `\|120` | ✅ |
| `\|240` | ✅ |
| `\|1D`, `\|2D` | ❌ **no acepta notación D** |
| `\|1W` | ✅ |
| `\|1M` | ✅ |

**Regla empírica:** el looper espera minutos exactos de la serie habitual de TradingView `1/5/15/30/60/120/240` + `1W`/`1M`. **No** acepta `2, 3, 10, 45, 180, 360, 720, 1D, 2D`. Nota: el base (sin sufijo) SÍ se comporta como el timeframe diario (respalda la conclusión de la v2 de que `close` base = cierre del día), y los sufijos `1D` simplemente no existen como sintaxis válida.

## 3 · Descubrimiento de campos filtrables (Test L)

Probe de 83 campos con el discriminador `greater (-1e9)` vs `greater (+1e9)`.

### 3.1 · Campos que SÍ filtran (58 confirmados)

**Indicadores (con y sin sufijo TF):** `RSI`, `RSI7`, `ADX`, `CCI20`, `BBPower`, `ATR`, `MACD.macd`, `MACD.signal`, `MACD.hist`, `Stoch.K`, `Stoch.D`, `W.R`, `Mom`, `ROC`, `Volatility.D`, `Volatility.W`, `Volatility.M`, `P.SAR`
**Performance:** `Perf.W`, `Perf.1M`, `Perf.3M`, `Perf.6M`, `Perf.Y`, `Perf.YTD`
**Precio/volumen:** `close`, `open`, `high`, `low`, `volume`, `change`, `change_abs`
**Fundamentales:** `price_52_week_high`, `price_52_week_low`, `average_volume_10d_calc`, `average_volume_30d_calc`, `number_of_employees`, `earnings_per_share_basic_ttm`, `revenue_per_share_ttm`, `operating_margin_ttm`, `gross_margin_ttm`, `net_margin_ttm`, `pricescale`
**Pivotes/otras:** `Pivot.M.Classic.R1`, `Pivot.M.Camarilla.R1`, `Pivot.M.Camarilla.R3`, `Recommend.All`, `gap`, `premarket_close`, `premarket_change`, `premarket_volume`
**Medias móviles / Bollinger:** `EMA10`, `EMA20`, `EMA50`, `SMA10`, `SMA20`, `SMA50`, `BB.upper`, `BB.lower`

### 3.2 · Campos que existen pero NO discriminaron con ±1e9 (requieren otra operación/umbral)

`Momentum`, `ROC21`, `TRIX`, `DMI.PDI`, `DMI.MDI`, `DMI.DX`, `Perf.D`, `RelVol`, `RelVolume_10d_calc`, `Value.Traded`, `market_cap_basic`, `total_shares_outstanding`, `float_shares_outstanding`, `P/E`, `P/S`, `P/B`, `Beta_1Y`, `target_mean_price`, `min_move`, `financial_rating`, `Pivot.D.Camarilla.R3`, `Pivot.W.Camarilla.R3`, `Analyst.Op.Recom`, `BB.middle`

> ⚠ La técnica ±1e9 es un cribado rápido. `market_cap_basic` y los shares tienen valores >1e9 para todos (por eso no discrimina con ese umbral); requieren umbrales realistas (ej. `market_cap_basic > 1e10`). Para confirmarlos con certeza convendría una prueba dirigida con la operación/umbral correcto.

### 3.3 · Campos que NO funcionan en `filter`

`update_mode`: el filtro numérico con `greater` lo rechaza (no es campo numérico; el string `delayed_streaming_900` no pasa el filtro). Si se quiere filtrar por modo, habría que usar operador `equal`/`in` — pendiente de probar.

### 4 · Limitación observada del endpoint: rate limit 429

Durante las pruebas previas (fase de descubrimiento manual, ~200 requests sin pausa) el endpoint devolvió **HTTP 429** (rate limited). La corrida v3 final se hizo con pausa de **1,2 s entre requests** (`REQUEST_DELAY_S`) y reintento en 429 (`MAX_RETRIES=3`) en `post_scan()` — no se volvió a tocar el límite.

**Implicación para producción (M-CAP-02 / F3.1):** un ciclo de 110 símbolos con 1 solo request POST no tiene problema. Pero el descubrimiento de campos filtra ~200 requests y **debe llevar pausa**.

### Reescritura de F3.1 (M-CAP-02)

El plan bloqueado de "POST único para 110 símbolos" **vuelve a ser viable**, con la ruta correcta:

```python
POST https://scanner.tradingview.com/america/scan?label-product=heatmap-stock

{
  "symbols": {"tickers": ["<110 símbolos>"]},
  "columns": ["close", "volume", "RSI", "RSI|15", "RSI|60",
              "ADX|15", "CCI20|15", "BBPower|15",
              "Pivot.M.Camarilla.R3", "Perf.W", "change",
              "gap", "premarket_close", "premarket_change", "premarket_volume"],
  "filter": [{"left": "RSI|60", "operation": "greater", "right": 60}]   # opcional
}
```

- 1 round-trip para los 110 símbolos (confirmado con 3 y con el universo completo en Test M).
- Puede sumarse `filter` con tiempo para pre-filtrar el radar sin procesar en cliente.
- Latencia medida: ~1,5 s por request (incluye pausa anti-429 de 1,2 s).
- **No requiere ThreadPoolExecutor**; el `Plan B` de la v2 queda descartado.

### Nota para la persistencia (ETL)

Si se agregan los campos `|TF` en las columnas del POST, el CSV/`fact_market_series` debe ampliarse igual que en F3.2 (base + bloque `|5` + bloque `|15`), y ahora también puede incluirse bloque `|60` para tendencia intradía de la sesión.
